## Что строим и зачем

Внутренний веб-инструмент для замены Qolio — платного сервиса оценки звонков.

**Проблемы с Qolio:** дорогая лицензия + неудобные отчёты + нет интеграции с Битрикс24.

**Пользователи:** 1–5 человек (руководитель + аналитики), компания Entera.

## Ключевые решения (договорённости)

### Чек-листы
- Структура: Чек-лист → Блоки → Критерии
- Оценка критерия: `yes` / `no` / `na` (Да / Нет / Не применимо) + текстовый комментарий
- Расчёт итога: `weighted` (взвешенный) или `average` (среднее) — задаётся на уровне чек-листа
- Все пользователи могут создавать и редактировать чек-листы (нет разграничения ролей)
- Активных чек-листов 2–3 одновременно; остальные архивируются

### Интеграция с Битрикс24
- Данные о сделках тянутся из MySQL Битрикс24 и кешируются в `deal_cache`
- Таблицы: `b24-entera-bitrix24-ru-deals`, `b24-entera-bitrix24-ru-deal-stages`
- Поиск сделки при создании оценки — по ID или имени оператора
- При поиске сделки `DealInfo` возвращает `presentation_date` — дата презентации, **поле зависит от отдела**:
  - Отделы продления → `UF_CRM_1654694803` (Продление дата "Провели презентацию")
  - Остальные отделы (ОП и др.) → `UF_CRM_1560328872` (общая "Дата презентации")
  - Если приоритетное поле пусто — берётся второе как запасное
  - **Определение «продления» — по дереву оргструктуры Битрикс**, а не по названию: отдел продления = узел «Продление» (ID `121`) или любой его потомок (`_RENEWAL_ROOT_DEPT_ID`, `_renewal_dept_ids()` в `bitrix.py`). Устойчиво к переименованиям и автоматически включает новые «Отдел продления N» под тем же родителем. Единственная зашитая величина — стабильный ID корня `121`
  - Запасной вариант `_is_renewal_department()` (сверка по названию «продлени») — если дерево недоступно
  - Логика: `_renewal_dept_ids()`, `_to_date()`, константы `_PRESENTATION_FIELD_RENEWAL/_GENERAL` в `bitrix.py`
  - **Причина фикса (08.07.2026):** раньше жёстко использовалось только поле продления, из-за чего у ОП в форму подставлялась `DATE_CREATE` вместо даты презентации
  - Кеш пересчитан скриптом `scripts/backfill_presentation_dates.py`; порог `_PDATE_MIGRATION` в `api.py` поднят до 08.07.2026 (пустые даты в старом кеше перезапрашиваются при поиске)
- Дата звонка в форме оценки: сначала `presentation_date`, при отсутствии — `DATE_CREATE`; поле остаётся редактируемым
- Метаданные полей хранятся в таблице `b24-entera-bitrix24-ru-fieldsnamings`

### Аналитика (`/reports`)
Два отчёта с навигацией в шапке:

**1. Общие показатели (`/reports`)** — фильтры без изменений, 3 вкладки:
- Тепловая карта сотрудников (блоки)
- Корреляция — связь баллов блоков с результатом сделки
- По сотрудникам — Won/Lost/Δ + Win Rate по уровням выполнения
- В конце вкладки «Общие показатели» — три дополнительных блока:
  - **Категория клиента vs Оценка** — бар (средний балл) + линия (Win Rate) по категориям A/B/C/D; только строки с заполненной категорией (отделы продления)
  - **Оценка vs Исход сделки** — 100% stacked bar (Won/Lost/В работе) по диапазонам оценки; корреляция уровня оценки с исходом
  - **Оценка vs Скорость закрытия** — сгруппированный бар: среднее дней от звонка до CLOSEDATE для Won и Lost по диапазонам; только закрытые сделки с известными датами
  - Логика: `compute_category_score()`, `compute_score_outcome()`, `compute_closing_speed()` в `analytics.py`; `attach_close_dates()` подтягивает `close_date` из `DealCache`
  - `DealCache` имеет поле `close_date` (CLOSEDATE из Битрикс); бэкфилл выполнен для всех 771 сделок в кэше

**2. Результаты сотрудников (`/reports/employee`)** — новый отчёт с расширенными настройками:
- Фильтры: период звонка, период оценки, отдел(ы), сотрудники, чек-лист, оценивал, стадия сделки
- Настройки отображения: % / баллы, разрез (группы / детально по критериям), показывать комментарии
- Таблица 1: Сводная тепловая карта (средние по сотрудникам + строка «Команда»)
- Таблица 2: Детализация (одна строка = одна оценка, ссылка на сделку в Битрикс24)
- Ссылки на сделки: `https://entera.bitrix24.ru/crm/deal/details/{deal_id}/`

Логика расчётов описана в `logic_summary.md`.

### Авторизация через Битрикс24 (OAuth2)
- Реализован OAuth2-вход через `https://entera.bitrix24.ru/oauth/authorize/`
- Маршруты: `GET /auth/bitrix24` (старт), `GET /auth/bitrix24/callback` (обработка кода)
- При первом входе пользователь создаётся автоматически: `username = email`, `full_name`, `bitrix_id`, `email`
- Модель `User` дополнена полями `bitrix_id VARCHAR(50)` (unique) и `email VARCHAR(200)`; `password_hash` теперь nullable
- Миграция: `ALTER TABLE users ADD COLUMN bitrix_id VARCHAR(50); ALTER TABLE users ADD COLUMN email VARCHAR(200);`
- Кнопка «Войти через Битрикс24» отображается только если заданы `BITRIX24_CLIENT_ID` в `.env`
- Форма логин/пароль остаётся как fallback для admin-пользователя
- Требует приложение в Битрикс24 (тип: Серверное): `https://entera.bitrix24.ru/marketplace/local/add/`
- Переменные `.env`: `BITRIX24_CLIENT_ID`, `BITRIX24_CLIENT_SECRET`, `BITRIX24_PORTAL=entera.bitrix24.ru`
- Redirect URI для приложения: `http://188.227.87.11:8550/auth/bitrix24/callback`

### Форма оценки — UX-решения
- Кнопки Да/Нет/Н/П — pill-форма с цветными контурами (зелёный/красный/серый), заливка при выборе
- `{% block styles %}` добавлен в `base.html` — без него CSS дочерних шаблонов игнорировался
- **Дата звонка** — readonly, заполняется из Битрикс (`DATE_CREATE`) при поиске сделки; без сделки пустая
- **Дата оценки** — readonly, проставляется автоматически при сохранении (`updated_at`); при первом создании = `created_at`
- Кнопки Редактировать/Удалить на странице просмотра оценки — перенесены в шапку (были внизу)
- **Телефон** — необязательное поле; если одна сделка имеет несколько звонков, телефон служит разделителем. Дубль-проверка: `deal_id + checklist_id + phone + evaluator_id` (NULL-телефон = отдельный «слот»). `evaluator_id` в ключе — чтобы калибровка работала: одну и ту же сделку могут оценивать разные пользователи; блокируется только повторная публикация той же сделки тем же пользователем. Миграция: `ALTER TABLE evaluations ADD COLUMN phone VARCHAR(50)`

- Поле `client_category` в `evaluations` пусто у 672+ строк из импорта (05.05.2026)

### Статус оценки (черновик / опубликована)
- Модель `Evaluation` имеет поле `status: "draft" | "published"` (по умолчанию `published`)
- В форме создания/редактирования — две кнопки: «Опубликовать» и «Сохранить черновик»
- Черновики **не попадают в аналитику** (`fetch_evaluations` фильтрует только `published`)
- На странице просмотра черновика — бейдж «Черновик» + кнопка «Опубликовать»
- При попытке опубликовать оценку с `deal_id`, который уже есть в опубликованной оценке того же чек-листа — автоматически сохраняется как черновик с предупреждением
- В списке оценок: бейдж «черновик» в колонке `#`, фильтр «Статус оценки» (Все / Опубликованные / Черновики)

### Метаданные чек-листа
- Модель `Checklist` имеет поле `updated_at: DateTime nullable` — обновляется при каждом сохранении настроек, публикации, архивировании
- Миграция: `ALTER TABLE checklists ADD COLUMN updated_at DATETIME`
- На странице `/checklists/{id}/settings` отображается: кто создал (full_name или username), дата создания, дата последнего изменения
- На странице `/checklists/{id}/edit` эти же данные показываются в шапке под названием чек-листа

### Чек-лист — привязка к отделам
- Модель `Checklist` имеет поле `departments: String(500)` — хранит через запятую названия отделов из Битрикс24
- Настраивается на странице `/checklists/{id}/settings` через чекбоксы
- Список отделов загружается через `get_departments()` из `bitrix.py`
- Если `departments` пустое — чек-лист доступен всем; фильтрация на стороне UI пока не реализована

### Калибровка (`/calibration`)

**Назначение:** сверка понимания чек-листа между сотрудником ОПП (регулярный оценщик) и внешним участником.

**Флаг оценки:**
- `Evaluation.is_calibration: Boolean` — отмечает оценку для калибровки
- Миграция: `ALTER TABLE evaluations ADD COLUMN is_calibration BOOLEAN DEFAULT 0`
- На странице просмотра оценки — кнопка «Отметить для калибровки» / «На калибровке»
- При нажатии: кнопка «Создать сессию калибровки» (ведёт на `/calibration/new?eval_id=N`)
- В списке оценок: красная точка у отмеченных + чекбокс-фильтр «Калибровка»

**Сессии (`CalibrationSession`):**
- Поля: name, description, session_date, source_evaluation_id, created_by_id, status (open/closed)
- Список: `/calibration`, создание: `/calibration/new`
- Просмотр: `/calibration/{id}` — список участников, их статус, кнопки

**Участники (`CalibrationParticipant`):**
- Добавляются при создании сессии или через форму на странице сессии
- Каждый участник оценивает независимо: `/calibration/{id}/evaluate/{pid}`
- Форма показывает инфо о сделке (но НЕ показывает ответы исходной оценки)
- После заполнения создаются `CalibrationAnswerItem` записи, participant.status = "completed"

**Сравнение (`/calibration/{id}/compare`):**
- Выбор активного участника (вкладки если несколько)
- Таблица: критерий | Исходная | Калибровка | Совпадение
- Зелёная строка = совпадение, красная = расхождение
- % совпадения в шапке
- Поле решения для каждого расхождения: final_value (Да/Нет/Н/П) + комментарий
- Сохраняется как `CalibrationItemResolution`

**Новые модели:**
- `CalibrationSession` — сессия
- `CalibrationParticipant` — участник (user_id, total_score, answers)
- `CalibrationAnswerItem` — ответы участника (criterion_id, value, comment)
- `CalibrationItemResolution` — итоговое решение по расхождению

**Роутер:** `app/routers/calibration.py`
**Шаблоны:** `app/templates/calibration/` (index, new, view, evaluate, compare)

- Роли пользователей (admin / reviewer) — отложено
