Внутренний веб-инструмент для замены Qolio — платного сервиса оценки звонков.

## Ключевые решения (договорённости)

### Чек-листы
- Структура: Чек-лист → Блоки → Критерии
- Оценка критерия: `yes` / `no` / `na` (Да / Нет / Не применимо) + текстовый комментарий
- Расчёт итога: `weighted` (взвешенный) или `average` (среднее) — задаётся на уровне чек-листа
- Все пользователи могут создавать и редактировать чек-листы (нет разграничения ролей)
- Активных чек-листов 2–3 одновременно; остальные архивируются

### Ежедневная синхронизация статусов сделок (23.07.2026)
**Причина:** стадия сделки (`Evaluation.stage`) записывалась ОДИН раз при создании оценки и больше не обновлялась; `deal_cache.stage` обновлялся только при повторном поиске сделки. Автоматического обновления не было вовсе. Итог: отчёты показывали снимок стадии на момент звонка, а кэш устаревал (напр., на 23.07 кэш держал майский снимок — 140 «в работе» вместо реальных 115 «успешных»). Проявилось на чек-листе «ТВК Продление Аудит»: отчёт показывал 1 провал, а в живом Битрикс их 2 (сделка 1399052 закрылась как проигранная уже после оценки).
- **Диагностика (важно на будущее):** стадия определяется по `STAGE_SEMANTIC_ID` живой сделки (`SEMANTIC_TO_STAGE`: `S`→успешна, `F`→провал, `P`/NULL→в работе). Переходы вида «успех→в работе» = устаревший кэш (сама сделка в Битрикс осталась `C5:WON`). Переходы «провал→в работе» бывают реальными — проваленную сделку переоткрывают в стадию `NEW` (`semantic=P`); это не баг.
- **Решение:** `scripts/sync_deal_stages.py` — проходит по всем сделкам из оценок и кэша, пакетно (`get_deal_stages_bulk()` в `bitrix.py`, один SQL на 500 id) берёт актуальные `STAGE_SEMANTIC_ID` + `CLOSEDATE`, обновляет `deal_cache.stage/close_date/last_synced_at` и `evaluations.stage` у всех оценок сделки. Есть `--dry-run` (обязательно прогонять перед применением на проде — база боевая). Отчёт менять не пришлось: он читает `ev.stage`, а тот теперь держится актуальным.
- **Автозапуск:** systemd `call-eval-sync.timer` → `call-eval-sync.service` (oneshot, `Type=oneshot`, `/usr/bin/python3 scripts/sync_deal_stages.py`), ежедневно `OnCalendar=*-*-* 06:00:00` (UTC = 09:00 МСК, `Persistent=true`). Unit-файлы версионируются в `deploy/`; установлены в `/etc/systemd/system/`. Управление: `sudo systemctl start call-eval-sync.service` (разово), `systemctl list-timers call-eval-sync.timer`, `journalctl -u call-eval-sync.service`.
- **Первый прогон (23.07.2026):** 888 сделок из Битрикс, 103 правки стадии в кэше, 9 в оценках (7 провал→в работе — переоткрытые, 1 провал→успех, 1 работа→провал). Чек-лист 9 после: 117 успешных / 68 в работе / 2 провала / Win Rate 98.3% — сошлось с Битрикс.

### Интеграция с Битрикс24
- Данные о сделках тянутся из MySQL Битрикс24 и кешируются в `deal_cache`
- Таблицы: `b24-entera-bitrix24-ru-deals`, `b24-entera-bitrix24-ru-deal-stages`
- Поиск сделки при создании оценки — по ID или имени оператора
- При поиске сделки `DealInfo` возвращает `presentation_date` — дата презентации, **поле зависит от отдела**:
  - Отделы продления → `UF_CRM_1654694803` (Продление дата "Провели презентацию")
  - Остальные отделы (ОП и др.) → `UF_CRM_1560328872` (общая "Дата презентации")
  - Если приоритетное поле пусто — берётся второе как запасное
  - **Определение «продления» — по дереву оргструктуры Битрикс**, а не по названию: отдел продления = узел «Продление» (ID `121`) или любой его потомок (`_RENEWAL_ROOT_DEPT_ID`, `_renewal_dept_ids()` в `bitrix.py`). Устойчиво к переименованиям и автоматически включает новые «Отдел продления N» под тем же родителем. Единственная зашитая величина — стабильный ID корня `121`
  - Запасной вариант `_is_renewal_department()` (сверка по названию «продлени») — если дерево недоступно
  - Логика: `_renewal_dept_ids()`, `_to_date()`, константы `_PRESENTATION_FIELD_RENEWAL/_GENERAL` в `bitrix.py`
  - **Причина фикса (08.07.2026):** раньше жёстко использовалось только поле продления, из-за чего у ОП в форму подставлялась `DATE_CREATE` вместо даты презентации
  - Кеш пересчитан скриптом `scripts/backfill_presentation_dates.py`; порог `_PDATE_MIGRATION` в `api.py` поднят до 08.07.2026 (пустые даты в старом кеше перезапрашиваются при поиске)
- Дата звонка в форме оценки: сначала `presentation_date`, при отсутствии — `DATE_CREATE`; поле остаётся редактируемым
- Метаданные полей хранятся в таблице `b24-entera-bitrix24-ru-fieldsnamings`

### Аналитика (`/reports`)
Два отчёта с навигацией в шапке:

**1. Общие показатели (`/reports`)** — фильтры без изменений, 3 вкладки:
- Тепловая карта сотрудников (блоки)
- Корреляция — связь баллов блоков с результатом сделки
- По сотрудникам — Won/Lost/Δ + Win Rate по уровням выполнения
- В конце вкладки «Общие показатели» — три дополнительных блока:
  - **Категория клиента vs Оценка** — бар (средний балл) + линия (Win Rate) по категориям A/B/C/D; только строки с заполненной категорией (отделы продления)
  - **Оценка vs Исход сделки** — 100% stacked bar (Won/Lost/В работе) по диапазонам оценки; корреляция уровня оценки с исходом
  - **Оценка vs Скорость закрытия** — сгруппированный бар: среднее дней от звонка до CLOSEDATE для Won и Lost по диапазонам; только закрытые сделки с известными датами
  - Логика: `compute_category_score()`, `compute_score_outcome()`, `compute_closing_speed()` в `analytics.py`; `attach_close_dates()` подтягивает `close_date` из `DealCache`
  - `DealCache` имеет поле `close_date` (CLOSEDATE из Битрикс); бэкфилл выполнен для всех 771 сделок в кэше

**2. Результаты сотрудников (`/reports/employee`)** — новый отчёт с расширенными настройками:
- Фильтры: период звонка, период оценки, отдел(ы), сотрудники, чек-лист, оценивал, стадия сделки
- Настройки отображения: % / баллы, разрез (группы / детально по критериям), показывать комментарии
- Таблица 1: Сводная тепловая карта (средние по сотрудникам + строка «Команда»)
- Таблица 2: Детализация (одна строка = одна оценка, ссылка на сделку в Битрикс24)
- Ссылки на сделки: `https://entera.bitrix24.ru/crm/deal/details/{deal_id}/`

Логика расчётов описана в `logic_summary.md`.

**Фикс подсветки в разрезе «детально по критериям» (09.07.2026):**
- Симптом: в отчёте «Результаты сотрудников» в разрезе критериев выбранное значение (Да/Нет/Н-П) не подсвечивалось на странице.

### Фикс: терялись недобавленные комментарии к критериям (13.08.2026)
- **Симптом:** в оценке 968 заполнявший напечатал комментарии к критериям, но они не сохранились (в БД все `evaluation_items.comment` пусты, `general_comment` NULL).
- **Причина:** поле ввода комментария `<textarea id="comment-input-{crit}">` не имеет атрибута `name` — на сервер напрямую не отправляется. Реально уходит скрытое поле `comments_json_{crit}`, которое заполняется только внутри `addOrUpdateComment()` (клик «+ Добавить» или Enter без Shift). Если пользователь напечатал текст и сразу нажал «Опубликовать», не «добавив» комментарий — текст остаётся только в textarea, а в скрытое поле уходит `[]` → `_read_comments_from_form()` пишет `None`. Черновик (localStorage) тоже не спасает: `saveDraft()` сохраняет только уже зафиксированные комментарии из JS-объекта `comments`, а при отправке черновик удаляется. Восстановить потерянные комментарии с сервера нельзя.
- **Фикс:** в обработчик `submit` формы `#eval-form` добавлен «флаш» — перед отправкой проходим по всем `[id^="comment-input-"]` с непустым значением и вызываем `addOrUpdateComment(critId)`, дозаписывая текст в скрытое поле. ### Калибровка (`/calibration`)

**Назначение:** сверка понимания чек-листа между сотрудником ОПП (регулярный оценщик) и внешним участником.

**Флаг оценки:**
- `Evaluation.is_calibration: Boolean` — отмечает оценку для калибровки
- Миграция: `ALTER TABLE evaluations ADD COLUMN is_calibration BOOLEAN DEFAULT 0`
- На странице просмотра оценки — кнопка «Отметить для калибровки» / «На калибровке»
- При нажатии: кнопка «Создать сессию калибровки» (ведёт на `/calibration/new?eval_id=N`)
- В списке оценок: красная точка у отмеченных + чекбокс-фильтр «Калибровка»

**Сессии (`CalibrationSession`):**
- Поля: name, description, session_date, source_evaluation_id, created_by_id, status (open/closed)
- Список: `/calibration`, создание: `/calibration/new`
- Просмотр: `/calibration/{id}` — список участников, их статус, кнопки

**Участники (`CalibrationParticipant`):**
- Добавляются при создании сессии или через форму на странице сессии
- Каждый участник оценивает независимо: `/calibration/{id}/evaluate/{pid}`
- Форма показывает инфо о сделке (но НЕ показывает ответы исходной оценки)
- После заполнения создаются `CalibrationAnswerItem` записи, participant.status = "completed"

**Сравнение (`/calibration/{id}/compare`):**
- Выбор активного участника (вкладки если несколько)
- Таблица: критерий | Исходная | Калибровка | Совпадение
- Зелёная строка = совпадение, красная = расхождение
- % совпадения в шапке
- Поле решения для каждого расхождения: final_value (Да/Нет/Н/П) + комментарий
- Сохраняется как `CalibrationItemResolution`

**Новые модели:**
- `CalibrationSession` — сессия
- `CalibrationParticipant` — участник (user_id, total_score, answers)
- `CalibrationAnswerItem` — ответы участника (criterion_id, value, comment)
- `CalibrationItemResolution` — итоговое решение по расхождению

**Роутер:** `app/routers/calibration.py`
**Шаблоны:** `app/templates/calibration/` (index, new, view, evaluate, compare)

**Несколько сделок в одной сессии (08.07.2026):**
- Сессия теперь может содержать несколько сделок (оценок-источников), все по одному чек-листу.
- Новые модели:
  - `CalibrationSessionEval` — сделка в составе сессии (`session_id`, `source_evaluation_id`, `order_index`)
  - `CalibrationParticipantEval` — прогресс/итог участника по одной сделке сессии (`total_score`, `general_comment`, `status`, `completed_at`)
- `CalibrationSession.checklist_id` — чек-лист сессии; `source_evaluation_id` оставлен для совместимости (= первая сделка).
- `CalibrationAnswerItem.session_eval_id` и `CalibrationItemResolution.session_eval_id` — привязка ответа/итога к конкретной сделке (NULL = legacy, единственная сделка).
- Миграция и идемпотентный бэкфилл старых сессий (одна сделка → одна запись) — в `_run_migrations()` (`app/main.py`); таблицы создаёт `create_tables()`.
- Маршруты: `POST /calibration/{id}/add-deal`, `POST /calibration/{id}/remove-deal/{session_eval_id}`; оценка и сравнение теперь по `session_eval_id`:
  - `GET/POST /calibration/{id}/evaluate/{pid}/{session_eval_id}` — после сохранения ведёт к следующей незаполненной сделке, затем назад в сессию
  - `GET /calibration/{id}/compare?pid=&se=` — сводка совпадения по всем сделкам + детализация по выбранной сделке
- Guard-ветки: нельзя удалить единственную сделку; нельзя добавить дубль/сделку другого чек-листа; закрытую сессию менять нельзя; при удалении первичной сделки `source_evaluation_id` переназначается на оставшуюся.
- Проверено e2e (08.07.2026): создание мультисделочной сессии, оценка обеих сделок, per-deal % совпадения, resolve, add/remove-deal, close — всё корректно.

**Подстановка собственной готовой оценки в форму (08.07.2026):**
- Если у участника калибровки уже есть своя опубликованная оценка по той же сделке и чек-листу — на форме оценки предлагается подставить её ответы одной кнопкой вместо заполнения заново.
- `_participant_own_evals()` в `calibration.py` — ищет опубликованные оценки участника (`evaluator_id == user_id`, тот же `deal_id`, тот же `checklist_id`, `status='published'`), исключая исходную оценку сессии; свежие первыми.
- `GET /calibration/{id}/evaluate/{pid}/{session_eval_id}?prefill={eval_id}` — подставляет ответы (`answer_map`) и общий комментарий из выбранной оценки в форму; **ничего не сохраняется** — пользователь проверяет и жмёт «Сохранить». `EvaluationItem` дуально совместим с шаблоном (`.value`/`.comment`), как `CalibrationAnswerItem`.
- Шаблон `evaluate.html`: алерт-предложение «У вас уже есть готовая оценка — подставить?» (кнопки по каждой оценке: дата · телефон · %) и алерт-подтверждение «Ответы подставлены из вашей оценки».
- Проверено e2e (08.07.2026): prefill корректно рендерит раскладку да/нет/н-п исходной оценки (34/34), сохранение POST пишет подставленные значения (форма → `CalibrationAnswerItem`).

**% совпадения в списке и на странице сессии (08.07.2026):**
- Раньше % совпадения ответов участника с исходной оценкой считался только на `/compare`. Теперь он же виден в списке сессий и в матрице сессии.
- `_session_match_pcts(sess)` в `calibration.py` — по полностью загруженной сессии возвращает: `pe_match {(participant_id, session_eval_id): pct|None}` (по сделке), `part_match {participant_id: pct|None}` (общий по участнику), `session_avg` (средний по участникам = итог сессии). Использует `_match_counts()`.
- **Взвешивание:** общий % по участнику = `matched/compared` по всем критериям обеих сделок в пуле (НЕ среднее per-deal). Т.е. сделка с большим числом сравнимых критериев весит больше.
- `calibration_index`: подгрузка расширена до полного графа (`checklist.blocks.criteria`, `session_evals.source_evaluation.items`, `participants.answers`), в шаблон идёт `session_match {session_id: avg}`. `index.html` — колонка «Совпадение» + бейджи участников.
- `calibration_view`: передаёт `pe_match`, `part_match`, `session_avg`. `view.html` — в матрице «сделки × участники» ячейка показывает % совпадения (крупно, цвет по `score_color`) и балл (мелко); в шапке участника — его общий %.
- Проверено e2e (08.07.2026): `/calibration` и `/calibration/5` отдают 200; значения из рендера совпали с прямым вызовом `_session_match_pcts` — сессия 5 (мультисделочная): per-deal 47.1%/3.3%, участник 26.6%, средний 26.6%; сессии 3/4: 84.8%/73.3%.

**Производительность: 504 при открытии `/calibration` и медленное сохранение (09.07.2026):**
- Симптомы: список калибровок отдавал 504; результат калибровки долго сохранялся.
- Причина: `_load_session()` и `calibration_index()` грузили сессию через `joinedload` сразу по трём независимым коллекциям (`checklist→blocks→criteria`, `session_evals→source_evaluation→items`, `participants→answers`) — SQLAlchemy склеивал их в один SQL-join → **декартово произведение** строк. Замер на 5 сессиях: `joinedload` 20.4 с против `selectinload` 0.037 с (×550). Сохранение медленное по той же причине: POST `evaluate` вызывает `_load_session`, затем редиректит на страницу сессии/сравнения.
- Фикс: коллекции грузятся через `selectinload` (отдельные `SELECT … IN`), many-to-one (`created_by`, `user`, `evaluator`, `source_evaluation`, `checklist`) — по-прежнему `joinedload`. Изменены `_load_session()` и `calibration_index()` в `calibration.py`; добавлен импорт `selectinload`.
- Проверено: `/calibration`, `/calibration/{id}`, `/compare` — 0.02–0.09 с, статус 200.

**Фикс сырого JSON в комментариях при подстановке своей оценки (10.07.2026):**
- Симптом: при подстановке собственной готовой оценки в форму калибровки (`?prefill=`) в поле комментария критерия появлялись «непонятные символы» — сырой JSON вида `[{"text": "...", "flag": "", "time": ""}]`.
- Причина: `EvaluationItem.comment` хранится как JSON-массив (rich-комментарии с флагом/таймкодом), а поле комментария в форме калибровки — plain text (`CalibrationAnswerItem.comment`). Prefill подставлял `EvaluationItem` напрямую (`.comment` → сырой JSON в `value` инпута).
- Фикс: класс-заглушка `_PrefillAnswer(value, comment)` в `calibration.py`; при prefill комментарий прогоняется через `_comment_text()` (JSON → читаемый текст). Обычные (не-prefill) ответы калибровки не затронуты — они и так plain text.

**Более очевидная тепловая заливка в матрице сессии (10.07.2026):**
- В `view.html` матрица «сделки × участники» раньше показывала % совпадения бледным бейджем `-subtle`.
- Теперь ячейка целиком заливается по `score_color(match%)` (классы `.match-cell-danger/warning/success` в `{% block styles %}`), % показан крупно (`.match-pct`). Красный/жёлтый/зелёный видны сразу.
